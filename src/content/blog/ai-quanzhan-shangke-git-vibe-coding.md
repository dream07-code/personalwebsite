# AI全栈上课：git入门+vibe coding个人网站

> 大家好，我是你们大二的学长。这篇文章是我给大一学弟学妹上的一节实操课的完整记录：用一个半小时，带大家从一个空文件夹开始，用 Claude Code 接 Mimo 模型 vibe coding 出一个自己的个人网站，顺带把 Git 最常用的操作过一遍。没来上课的学弟学妹也不用可惜，照着这篇从头做到尾，效果是一样的。

## 前言

学计算机的，几乎人手一个个人网站。不是因为作业要求，而是因为它太好用了——它就是你的简历，只不过比简历活得多，是一份会动的简历。

纸面简历写得再好，别人也只能信你一半。个人网站不一样，点开一个项目就能看到你真正做过什么：代码写得怎么样、思路是什么、遇到问题是怎么解决的。以后无论是找实习、进社团、组队做项目，还是单纯想让别人认识你，发一个链接过去，比发一堆截图和自我介绍都管用，对方一下子就对你有数了。

而且它不是做完就扔的东西，它会跟着你长大。大一先搭个架子，放一句自我介绍和一个刚跑起来的页面；到了大二、大三，文章、项目、踩过的坑会一点点加上去。几年下来，回头看就是你这几年是怎么过来的。

所以今天这节课，我们不聊虚的、不讲大道理，就带你们从零做出第一个属于自己的个人网站。做完它，你就有了第一个能拿出手、能发给别人的链接。

先说清楚这节课的玩法，免得大家一上来就懵：

- **从零开始，不抄现成仓库。** 不克隆任何模板，网站是你们自己写提示词、让 AI 一步步做出来的，做完它就是独一无二的，只属于你。
- **顺序一次走完，不来回折返。** 先初始化仓库、建仓库、完成第一次提交，再打开 Claude Code 填提示词开做，然后跑起来、微调。跟着顺序走就行，别跳步。
- **课上只做到本地完善并推上 GitHub。** 部署到 Cloudflare 这一步学长故意留成课后作业，回家不赶时间慢慢弄，反而记得更牢。
- **提示词少给限制，多给方向。** 现在的 AI 已经很聪明了，你把想要的感觉说清楚，剩下的让它自由发挥，做出来的东西经常比学长预想的还好。这篇里学长只守三条底线，其余全放开。

这节课走完，你能带走这些：

- 一个自己的 GitHub 仓库和一个本地能跑起来、内容全是你的个人网站；
- Git 的基本功：`init`、`add`、`commit`、`push`，外加看懂分支和远端仓库是怎么回事；
- 一套能复用的 vibe coding 方法：怎么写提示词、怎么放行 AI、怎么用大白话微调、报错了怎么处理。

全流程顺序：

1. 初始化仓库
2. 建仓库
3. 第一次提交
4. 填提示词开做
5. 跑起来
6. 微调
7. 课后作业：部署

## 只守三条底线，其余都放开

1. **密钥绝不进代码、绝不进仓库、绝不发到聊天里。** AI 向你要密钥，停下来举手问学长。
2. **不付费。** 要开通付费服务才能用的功能，直接让 AI 换个免费做法或去掉。
3. **个人信息不编造。** 学校、经历、作品只能写你真实的；拿不准的先空着，课后补。

除了这三条，技术选型、页面安排、配色设计，都先听 AI 的方案，你觉得顺眼就放行。

## 课前必做：先注册好 GitHub 账号

不要留到课上注册，课上现注册会卡在邮箱验证上。请在上课前完成，并把用户名记在手机备忘录里：

1. **邮箱：**用常用且能正常收邮件的邮箱，后面设置 Git、部署 Cloudflare 都用同一个。
2. **注册：**打开 github.com 点 Sign up，依次填邮箱、密码、用户名，完成人机验证。
3. **用户名：**只能用英文字母、数字和单个连字符（-），不能以连字符开头或结尾，全网唯一；它会出现在仓库地址里（github.com/你的用户名），建议姓名拼音加数字，不要中文和空格。
4. **密码：**至少 15 位，或至少 8 位且同时包含数字和小写字母；不要与其他账号共用，不发给任何人。

最后去邮箱点验证链接，能正常登录才算完成。没赶上的同学课上先在本地跟做，仓库先建在本地，课后补注册再按「第二步、第三步」补推。

## 这篇文章怎么用

- **给 Claude Code 的提示词**放在引用块里：照着打，把 `【】` 换成你自己的内容。
- **终端命令**放在代码块里：一行一行敲，敲完一行按一次回车。Git 命令行尾的 `#` 后面是注释，写的是这一条命令干了什么，不用敲进去。
- 每一步末尾都有验收动作。验收不过先看「卡住对照表」，再举手。

课上按上面的顺序一次走完：先仓库，后开做，最后微调。部署不在课上做，是课后作业。

| 环节 | 时长 | 做什么 |
| --- | ---: | --- |
| 开场 + 环境验证 | 10 分钟 | 逐项验证下面的清单；GitHub 只花 2 分钟确认能登录 |
| 初始化仓库 + 建仓库 + 第一次提交 | 20 分钟 | 本地初始化，GitHub 建空仓，第一次提交并推送成功 |

| 跑起来 + 验收 | 10 分钟 | 本地打开网站，逐页点一遍，报错当场清掉 |

## 二、前置清单：课前先备好，现场只验证

- [ ] **GitHub 账号（课前注册好）：**能登录、邮箱已验证，记得住用户名。没注册的先本地跟做，课后补。
- [ ] **Git：**终端能跑 Git 命令；第一次用先设好名字和邮箱（命令在下面）。
- [ ] **Node.js 22 或更高版本：**版本低了依赖会装不上。
- [ ] **Claude Code，且已接好 Mimo 模型：**课前已完成接入，现场只确认能正常回话，不重新配置。

逐项验证（在终端里敲）：

```bash
git --version # 查看 Git 版本，确认 Git 已装好、能用
node --version # 查看 Node.js 版本，确认是 v22 或更高
npm --version # 查看 npm 版本，确认装依赖的工具能用
```

预期：三条都打印版本号，Node 为 v22 或更高。

第一次用 Git 的，再敲下面两行，引号里换成你自己的名字和注册 GitHub 用的邮箱，只需设一次：

```bash
git config --global user.name "你的名字" # 告诉 Git 提交时作者名字写谁，全局设一次就行
git config --global user.email "你的邮箱" # 告诉 Git 提交时作者邮箱写哪个，要和 GitHub 注册邮箱一致
```

### 验证 Claude Code + Mimo

在任意文件夹打开终端启动 Claude Code，只问一句话确认能回话：

> 你好，请用一句话介绍你自己，并告诉我你现在用的模型是什么。

能正常回复就到此为止，不要再动任何配置。配置内容按课前配好的来，这篇文章里写成【按课前配置填】；启动报错先看网络，再举手，不要自己上网搜一套配置照着改，更不要把密钥发给任何人。


## 三、第一步：初始化仓库

先有仓库，再写网站，每一次改动就都有记录，改坏了也能退回来。这一步只做本地仓库，还不碰 GitHub。

### 1. 新建项目文件夹

在电脑上找一个路径短、全英文的位置（例如 D 盘根目录），新建文件夹 `my-website`。名字只用英文、数字和连字符，不要中文、不要空格，后面能省掉很多路径报错。在这个文件夹里打开终端，往下敲。

### 2. 初始化本地仓库

```bash
git init # 在当前文件夹初始化一个本地 Git 仓库，生成隐藏的.git 文件夹来保存版本记录
git branch -M main # 把默认分支改名为 main，和 GitHub 上的主分支名保持一致
```

验收：终端出现 `Initialized empty Git repository` 一类的提示，文件夹里多出一个隐藏的 `.git` 文件夹。看不到隐藏文件是正常的，不用管它，更不要删它，删了仓库就没了。

### 3. 先写好 .gitignore

在项目文件夹里新建一个名为 `.gitignore` 的纯文本文件，内容就这几行。它的作用是告诉 Git：这些东西不要收进仓库。

```text
node_modules/
dist/
.env
.env.*
*.local
```

> **把.env 这件事一次说清：**这个项目是纯前端静态网站，本来就没有 `.env` 这个文件，也不用新建。上面把 `.env` 写进 `.gitignore`，只是以防万一的预防规则，跟挡住 `node_modules` 是一回事，不代表项目里有这个文件。Mimo 的密钥在你电脑上 Claude Code 自己的配置里，在项目文件夹外面，不会跟着网站走。后面如果 AI 让你新建 `.env`、往里填密钥，那是它跑偏了，停下来举手，不要照做。

### 4. 写一个最简单的 README

新建 `README.md`，先写三行就行，课后作业时再往里补线上网址：

```markdown
# 我的个人网站
用 Claude Code + Mimo 从零做的个人网站。
线上网址：课后部署完成后填在这里。
```

**本步验收：**文件夹里有 `.git`（隐藏）、`.gitignore`、`README.md` 三样东西。齐了就做下一步，把它接到 GitHub 上。

## 四、第二步：建仓库；第三步：第一次提交

本地仓库已经建好。这一步把它接到 GitHub，并完成你的第一次提交和第一次推送。做完这一步，后面写网站时每次推送都只是重复最后两条命令。

### 第二步：在 GitHub 上建一个空仓库

1. 登录 github.com，点右上角 + 号，选 New repository。
2. 仓库名填和本地文件夹一样的名字，例如 `my-website`；可见性选 Public。
3. 不要勾选 Add a README file，也不要加.gitignore 和 license，必须建一个完全空的仓库，否则第一次推送会冲突。本地已经有 README 了，不需要它再生成一份。
4. 点 Create repository，把页面给出的仓库地址留好，下一步要用。

### 第三步：第一次提交并推送

回到项目文件夹的终端，先接上远程仓库：

```bash
git remote add origin https://github.com/【你的用户名】/【仓库名】.git # 把 GitHub 上刚建的空仓库登记为远程仓库，起个名叫 origin
```

把【你的用户名】和【仓库名】换成你自己的，也可以直接从仓库页面复制它给出的地址。然后完成第一次提交：

```bash
git add . # 把当前文件夹里所有新文件和改动都放进暂存区，准备提交
git status # 查看哪些文件将被提交，确认没有多余的东西混进来
git commit -m "init: 初始化仓库" # 把暂存区的文件正式存成一次提交，-m 后面是这次提交的说明
git push -u origin main # 把本地 main 分支第一次推到 GitHub 的 origin 仓库，并记住以后默认就推这里
```

`git status` 这一步是让你亲眼确认：要提交的只有 `README.md` 和 `.gitignore` 两个文件，没有别的东西混进来。

> **第一次 push 的登录，别填账号密码。** GitHub 已经不接受用账号密码做 push：
>
> - 弹出浏览器窗口时，选在浏览器中登录并同意授权，优先走这种。
> - 终端问 Username / Password 时，Username 填用户名，Password 粘贴个人访问令牌，不是账号密码（粘贴时不显示字符是正常的）。令牌在 GitHub 的 Settings → Developer settings → Personal access tokens → Tokens (classic) 里生成，勾选 repo；它只显示一次，当场保存，不要发给任何人、不要写进代码。

**本步验收：**刷新 GitHub 仓库页面，能看到 README 和.gitignore，提交记录里有 `init: 初始化仓库`。

没注册上 GitHub 的同学：先做到 `git commit` 为止，课后补注册、建空仓，再补 `git remote add` 和 `git push` 两条，本地的提交不会丢。


## 五、提示词怎么写：少给限制，多给方向

学长这节课的提示词写法，和网上很多教程不太一样。很多人怕 AI 乱来，会把技术、页面、步骤全规定死；实际上现在的 AI 能力足够强，限制堆得越多，它的好想法越施展不开，做出来的东西反而千篇一律。学长的写法是：把「想要什么」说清楚，把「怎么做」交给它。

| 写法 | 样子 | 结果 |
| --- | --- | --- |
| 限制型（不用） | 指定框架、指定文件结构、一步步规定先做哪个文件 | AI 只剩执行你的方案，你想不到的好设计永远不会出现 |
| 放开型（本课用这个） | 只说我是谁、想要什么感觉、必须有的最少内容、守住三条底线，其余请它提方案 | AI 会给出你没想到的布局、配色和细节，每个人做出来的站都不一样 |

### 放开，不等于什么都不说

要给足的是这四样，给足了就可以撒手：

- **我是谁：**姓名或昵称、学校专业、一句话介绍、爱好或想展示的东西。这是网站的原料，只能你给。
- **想要的感觉：**用几个词形容就行，例如「干净、年轻、有点酷」「温暖、像手账」。形容词比指定色号管用，AI 会自己翻译成设计。
- **必须有的：**只列底线内容，例如要有首页、能找到我的联系方式。其余页面让它建议。
- **三条底线：**就是开头那三条，密钥、付费、编造经历，除此之外不再加限制。

判断标准很简单：你的提示词里，「我想要……」应该多于「你必须……」。发现自己写了一串「必须用某某、不许某某」，删掉一半，只留底线，然后看 AI 能给你什么惊喜。不满意再往回收，永远来得及；一开始就锁死，好想法根本没机会出现。

下一节就是按这个写法成的总提示词正文，填好个人信息就能直接发。

## 六、总提示词正文（填好个人信息，整段发送）

开做时才发送，先看一遍它长什么样。注意它有多「松」：没有指定框架，没有规定文件，没有排步骤，只给了人和方向。

> 我想做一个属于我自己的个人网站，请你帮我从零做出来。
>
> 技术方案、页面安排、视觉设计都由你来提议，发挥你的想法，做出一个让人打开就记住我的网站，不要做成千篇一律的模板。
>
> 关于我：
>
> - 我是【姓名或昵称】，【学校 + 专业 + 年级】。
> - 一句话介绍我：【例如：喜欢拍照和捣鼓代码的大一新生】
> - 我喜欢 / 擅长 / 想展示的：【例如：摄影、Python、羽毛球；没有就先写还没想好】
> - 联系方式只放：【例如：GitHub 链接 + 邮箱，不要放手机号】
>
> 我想要的感觉：【例如：干净、年轻、有点酷，或温暖、文艺、像一本手账】
>
> 必须有的只有两样：一个能介绍我的首页，和能联系到我的方式。其他页面你看着建议，比如关于我、作品、博客，你觉得哪个适合我就做哪个，页面数量和内容你来安排。
>
> 动手前先用几句话告诉我你的方案：打算用什么技术、做哪几个页面、设计上有什么想法。我看顺眼就会让你直接做，不用等我逐条批准；方案里如果有要花钱的服务、要填密钥才能用的功能，先换掉再告诉我。
>
> 只提醒三件事：
>
> 1. 不要编造我的经历、奖项和作品，没有的就留空位并告诉我；
> 2. 不要把任何密钥、令牌写进代码；
> 3. 做完告诉我怎么在本地打开它看效果。

### 想再放开一点，或者收一点

- **想让它更野：**在提示词最后加一句「设计上可以大胆一点，动效、排版、配色都由你决定，我只看最终效果」。
- **想要某种风格：**不用查术语，直接说参照物，例如「像唱片店海报那种感觉」「像苹果官网那样简洁」，AI 能听懂。
- **有明确不想要的：**只写最不能接受的一两样，例如「不要满屏渐变紫」，别列十条禁令。


## 七、第四步：在 Claude Code 里填提示词，正式开做

仓库已经推上 GitHub 了，现在才打开 Claude Code。注意位置：在项目文件夹里启动它，它才知道在哪个仓库干活。

### 1. 发送总提示词

把上一节那段提示词整段发过去。发送前最后扫一眼：`【】` 都换成你自己的内容了，没有留空。

### 2. 看它的方案，顺眼就放行

它会先回一段方案：用什么技术、做几个页面、设计想法是什么。这一步你只需要做一个判断：大方向顺不顺眼。顺眼就直接回一句：

> 方案可以，就按你说的做。一次做完，做到能在本地打开看效果为止，中间不用每步都停下来问我。做完把改了哪些文件、怎么打开，一起告诉我。

只有两种情况要拦一下：一是方案里冒出要付费、要填密钥的东西，让它当场换掉；二是它把你的个人信息理解错了，例如学校、名字写错。细节不合心意先别拦，记下来，留到微调时一起改，那时候看着实物改比现在空想准得多。

### 3. 等它做完，顺手提交一次

它干活时屏幕上会滚动新建和修改的文件，别中途打断，也别关终端。等它报告完成，先别急着看效果，在终端里把初版存进仓库：

```bash
git add . # 把 AI 刚新建和修改的所有文件放进暂存区，准备提交
git commit -m "feat: 网站初版" # 把这一版正式存成一次提交，说明是网站初版
git push # 把这次提交推到 GitHub，远程仓库和分支已经在第一次推送时记住了
```

这时它可能会改动 `.gitignore`，例如补上它那套工具要忽略的目录，这是正常的。只要文件列表里没有密钥、没有 `node_modules` 被提交进来，就没问题。

**本步验收：**GitHub 仓库页面刷新后能看到一堆网站源码文件，最新提交是 `feat: 网站初版`。下一步把它跑起来。

## 八、第五步：跑起来，亲眼看到你的网站

代码写完不算数，能在浏览器里打开才算数。这一步只做一件事：把网站在本地跑起来，逐页看一遍。

### 1. 用它给的命令启动

AI 做完时已经告诉过你打开方式，常见是先装依赖、再启动预览，在项目文件夹的终端里敲（以它告诉你的为准）：

```bash
npm install # 按项目清单把依赖包下载到 node_modules，第一次运行前要先装
npm run dev # 启动本地预览服务器，改代码后页面会自动刷新
```

终端会给出一个本地地址，常见是 http://localhost:4321 或 http://localhost:5173，以终端打印的为准。在浏览器里打开它。

看到页面的那一刻，先别挑毛病，先确认三件事：首页打开是你的名字和介绍；导航能点到其他页面再点回来；页面上没有别人的示例人名和 Lorem ipsum 这类假文字。三件都对，初版就算成立，具体好不好看是下一步微调的事。

### 2. 预览开着别关

跑着预览的那个终端不要关、不要在里面敲别的命令。你改代码时页面通常会自动刷新；没刷新的手动刷新浏览器即可。后面微调全程都开着它，改一处看一处。

### 3. 起不来时，把报错原样还给它

如果终端一片红字或页面白屏，不要自己猜，也不要删文件重来。把完整的报错文字复制下来发回给 Claude Code：

> 网站没跑起来，报错原文如下，你来判断原因并修好，修好后告诉我重新打开的命令和地址：
>
> 【把报错完整粘贴在这里，一字不改】

它修完后重新打开确认。修好记得补一次提交：

```bash
git add . # 把修复改动过的文件放进暂存区，准备提交
git commit -m "fix: 修复本地启动问题" # 把这次修复正式存成一次提交
git push # 把这次修复推到 GitHub，和线上仓库保持一致
```

**本步验收：**本地地址能打开、每个页面都点过一遍、手机宽度下（把浏览器窗口拉窄）文字不溢出。常见小毛病先翻「卡住对照表」，多半是端口被占用或预览被关了。


## 九、第六步：微调，把它改成你的样子

初版是 AI 的品味，微调是把你的品味加进去。方法很简单：看着页面，用大白话说你想要的变化，不用懂术语，不用说文件在哪。下面这些话都可以直接照着说：

| 想改什么 | 直接这样说 |
| --- | --- |
| 整体感觉 | 「现在的配色太素了，换成更年轻一点的，主色你来挑，挑完给我看效果。」 |
| 首页 | 「首页第一屏太空了。把我的名字放大，加一句我最想说的话，具体怎么排版你来设计。」 |
| 内容 | 「关于我那页把我这段话换进去：【粘贴你自己写的介绍】。其他段落帮我顺一下语气，不要改意思。」 |
| 加东西 | 「加一个展示我照片/作品的区块，形式你来想，先放三张占位图，告诉我以后把图放在哪个文件夹替换。」 |
| 手机端 | 「我把窗口拉窄看了，导航挤成一团。你按手机屏幕重新排一下，改完告诉我怎么自己再检查一遍。」 |

### 微调的节奏：一次一类，改完就存

1. 一次只提一类改动，例如这一轮只改配色，下一轮只改首页。一次说五件事，它容易漏，你也看不清哪件改坏了。
2. 每次改完先在浏览器里看效果。满意，再在终端里提交并推送；不满意，直接跟它说哪里不对，让它接着改，不要将就着提交。
3. 说不清想要什么时，让它先给选项：「给我三个配色方案，各说一句特点，我挑一个。」挑比想容易。

```bash
git add . # 把这一轮微调改过的文件放进暂存区，准备提交
git commit -m "style: 【这一轮改了什么】" # 把这一轮微调正式存成一次提交，说明里写清改了什么，例如：换主色与首页排版
git push # 把这一轮微调推到 GitHub，保存好这一版
```

> 微调时守住两点：一是越改越不像你的时候要喊停，回一句「撤掉这一轮，回到上一版的样子，我们换个方向」；二是别在微调里塞新底线外的要求，例如临时让它接要密钥的服务，那还是底线问题，按三条底线处理。

**本步验收：**你至少完成两轮微调并各提交一次；下课前最后确认一次 GitHub 上就是你眼前这一版。剩下的打磨和部署，回家按课后作业慢慢做。

## 十、卡住对照表：先自查，再举手

遇到问题先在这张表里找，找到就按「先这样做」处理，一般两三分钟能解决。试过还不行，把你试了什么一起告诉学长。

| 现象 | 先这样做 | 给 AI 的话 |
| --- | --- | --- |
| AI 跑偏：做了没要求的东西，或把做好的改坏了 | 先让它停，说清刚才动了哪些文件。已经提交过的版本随时能退回来，别慌，更不要删文件夹重开 | 「停。只改【具体问题】，其他不要动。实在不行就回到上一次提交的样子。」 |
| 依赖装不上：装包时一片红字 | 先看 Node 是不是 22 以上；换个网络再试一次；把红色报错最后十几行留好，不要反复重装十次 | 把报错原文粘给它，补一句：「先判断是版本、网络还是依赖冲突。」 |
| 端口被占用：预览起不来，提示地址已被使用 | 多半是之前开的预览没关。回到那个终端按 Ctrl+C 停掉，再重新启动；还不行让 AI 换个端口 | 「端口被占用了。换一个可用端口启动，告诉我新地址，不要动项目文件。」 |
| Windows 路径问题：找不到文件、路径报错 | 检查文件夹名有没有中文和空格、路径是不是太深。最稳妥是把项目放在纯英文短路径下，例如 D 盘根目录的 my-website，移完重跑命令 | 把完整报错和项目完整路径一起粘给它，问：「这是不是路径问题？移完要重跑哪几条命令？」 |
| 页面白屏 / 改了没反应 | 先硬刷新（Ctrl+F5）；再确认预览终端还开着；最后才怀疑代码 | 「页面白屏，我已经硬刷新、预览也在运行。从最可能的原因开始查，一次只查一个。」 |
| 它要你填密钥 / 付费开通 | 立即停下，不要填、不要付。这节课不需要任何新密钥和付费服务 | 「这个功能换成不需要密钥、不需要付费的做法；做不到就去掉。」然后举手告诉学长 |
| push 被拒 / 提示要用令牌 | 不要反复输账号密码。按第三步处理：浏览器登录，或在 Password 处粘个人访问令牌 | 这一步不用问 AI，令牌不要粘给 AI 或任何人 |

举手时说清三件事：你做到第几步、屏幕上完整的报错是什么、你已经试过对照表里的哪一条。


## 十一、学长演示：Git 进阶——分支和远端仓库（只演示，不在网站仓库里做）

这一节和前面的流程分开：**只由学长演示，学弟学妹们看和记概念就行，不要在 `my-website` 里跟着敲。** 演示全程用另一个练习仓库 `git-playground`，网站仓库从头到尾只用一条 `main` 分支，不受任何影响。

为什么还要讲这一节：课上你们只用到了「在 main 上提交、push 到 GitHub」，但真正多人协作、改大功能不敢直接动 main 的时候，靠的就是分支；代码在本地和 GitHub 之间来回同步，靠的就是远端。先把概念看明白，以后真用时不会慌。

### 先把概念说清

| 概念 | 一句话理解 |
| --- | --- |
| 分支 branch | 一条独立的时间线。在新分支上怎么改，都不影响 main，改好了再合回去 |
| 当前分支 | 你现在站在哪条时间线上，`git branch` 里带 `*` 的那条就是 |
| 远端 remote | GitHub 上那份仓库的代称，默认叫 `origin`。本地仓库和远端是两份独立的副本 |
| 远端分支 | 远端状态在本地的镜像，写作 `origin/main`、`origin/功能分支名`，只能看，不能直接在上面改 |
| `fetch` | 只把远端的最新状态下载回来看看，**不改**你本地正在写的文件 |
| `pull` | `fetch` + 合并：下载回来并直接合进你当前的分支，一步到位 |
| `clone` | 把一个远端仓库完整复制一份到本地，新电脑接手项目、或拿一份干净副本时用 |
| `merge` | 把一条分支的改动合进另一条分支，分支演示的最后一步就是它 |

记住一条主线就行：**分支管「分开改」，远端管「同步」，fetch / pull 管「把远端的新东西拿回来」。**

### 演示准备：另建一个练习仓库

在 GitHub 上再建一个完全空的仓库，名字叫 `git-playground`（建法和第四节建仓库一模一样：Public、什么都不勾）。然后在电脑上另找一个文件夹（不要放进 `my-website` 里面），把这个练习仓库克隆下来演示：

```bash
git clone https://github.com/【你的用户名】/git-playground.git # 把远端练习仓库完整复制一份到本地，复制完会自动进到一个同名文件夹里
cd git-playground # 进入刚克隆下来的练习仓库文件夹，后面的演示都在这里敲
git remote -v # 查看这个本地仓库连着哪些远端，确认 origin 指向 GitHub 上的 git-playground
git branch # 查看本地有哪些分支，空仓库还没有任何提交，这里暂时是空的，第一次提交之后才会出现 main
```

先在练习仓库里新建一个 `README.md`（随便写一行字就行），提交推送一次，让练习仓库里有点东西可演示：

```bash
git add . # 把练习文件放进暂存区，准备提交（演示仓库里的操作，和网站仓库无关）
git commit -m "init: 练习仓库初始化" # 把练习文件正式存成第一次提交
git push -u origin main # 把练习仓库的 main 第一次推到它的 origin，并记住默认推送目标
```

### 演示一：开一条分支改东西，再合回 main

场景：在分支上改坏了也不怕，main 始终是好的。

```bash
git switch -c feature/change-readme # 新建一条叫 feature/change-readme 的分支，并立刻切换到这条分支上
git branch # 再看一次分支列表，* 已经跑到 feature/change-readme 前面，说明你现在在这条线上改
```

这时在练习仓库里改一下 README（随便改一行字就行），然后：

```bash
git add . # 把分支上的改动放进暂存区，准备提交
git commit -m "feat: 在分支上改 README" # 把改动存成一次提交，注意这次提交只属于 feature/change-readme 这条分支
git switch main # 切回 main 分支，再打开 README 你会发现它又变回改之前的样子，分支上的改动没有跟过来
git merge feature/change-readme # 把 feature/change-readme 分支的改动合并进当前所在的 main 分支
git branch -d feature/change-readme # 合并完成后删掉这条本地分支，活已经干完、成果已经进 main，留着只会越攒越多
```

看点就两个：一是切回 main 时文件会自己变回去，分支之间是隔离的；二是 merge 之后改动才真正进 main。

### 演示二：把分支推到远端，在 GitHub 上看分支

分支不只在本地，也能推到 GitHub 上，这样队友能看到、以后发 Pull Request 也是从这一步来的。

```bash
git switch -c feature/add-note # 再新建一条演示分支并切换过去，随便改一行再提交一次（add / commit 和演示一一样，这里不重复）
git push -u origin feature/add-note # 第一次把这条分支推到远端 origin，并在本地记住它对应远端的同名分支
```

推完打开 GitHub 上 `git-playground` 的页面：分支下拉里能看到 `feature/add-note`，点进去能看到它和 main 的差别。这就叫远端分支——本地推上去之后，远端多了一条同名分支，本地也会多一个 `origin/feature/add-note` 的镜像。

演示完删掉它，保持练习仓库干净：

```bash
git switch main # 先切回 main，站在要删的分支上是删不掉它自己的
git branch -d feature/add-note # 删掉本地的这条演示分支
git push origin --delete feature/add-note # 删掉远端 origin 上的同名分支，本地删和远端删是两件事，要分开做
```

### 演示三：远端有了新提交，fetch 和 pull 有什么区别

场景：你在本地写代码，同伴直接在 GitHub 网页上改了 README——远端比你新了，怎么拿回来？学长现场在 GitHub 网页上打开练习仓库的 README，点编辑改一行并提交，然后回到本地终端：

```bash
git fetch # 只把远端的最新状态下载回来，更新 origin/main 这个镜像，但不改你本地 main 正在写的文件
git status # 查看本地 main 和 origin/main 的差距，这时会提示你的分支落后远端几个提交
git log --oneline main..origin/main # 只看远端比本地多出来的那几个提交，确认就是同伴在网页上改的那次
git pull # 把远端的新提交下载并直接合并进本地 main，pull 等于 fetch 加 merge 一次做完
```

区别一句话：**fetch 是先看看，pull 是直接拿过来用。** 不确定远端改了什么、怕冲掉自己正在写的东西时，先 fetch 看清楚再 pull；确定没冲突，平时直接 pull 就行。你们课后自己维护网站时，如果只在一台电脑上写，一般用不上 pull；换电脑、或在网页上改过文件，再打开本地仓库时，先 pull 一次最稳。

### 演示四：clone 一份干净副本（可选，30 秒看完即可）

```bash
git clone https://github.com/【你的用户名】/git-playground.git git-playground-copy # 把同一个远端仓库再完整复制一份到新文件夹，模拟换一台电脑从零接手项目
```

看点：clone 下来的文件夹里带着完整的提交历史，不是一份光秃秃的文件拷贝。这也是为什么课前没注册上的同学课后补推没问题——历史一直在本地 `.git` 里。

### 演示收束：回到网站时只需要记住这些

- 个人网站仓库全程只用 main：`add` → `commit` → `push`，课上这套足够。
- 分支是给「不敢直接动 main」和「多人协作」准备的，今天只要求看懂：开分支、切分支、合回 main、删分支。
- 远端默认叫 origin；push 是把本地推上去，fetch 是先下载看看，pull 是下载并合并，clone 是整份复制。
- **不要拿网站仓库练分支。** 想练手，回家在 `git-playground` 里随便练，练坏了删掉重建，不心疼。

## 十二、课后作业：把网站部署到 Cloudflare Pages

课上到微调和推送为止。部署回家做，不赶时间，按下面顺序一次做完。部署成功之后，每次推送到 main，线上网站都会自动更新。

### 先把内容完善好，再部署

1. **完善内容：**全站换成你的真实信息，不留示例人名、占位文字和编造的经历；课上留的空位补上；放一张真实图片替换占位图。改完照微调的节奏提交并推送。
2. **本地先构建一次：**让 Claude Code 告诉你构建命令并跑通（常见是 `npm run build`），记下构建命令和构建产物目录，部署时照着填。本地构建不过，先按第八节「跑起来」里的方法把报错给它修好，不要带着错误去部署。

### 部署五步

1. 用注册 GitHub 的同一个邮箱注册 Cloudflare 免费账号并完成邮箱验证，密码不外传。
2. 进入 Workers & Pages，创建 Pages 项目，连接 Git，选择课上建的那个仓库。
3. 生产分支选 main；构建命令和产物目录填上一步记下的值，和本地不一致时以本地为准。
4. 点部署，等状态变成成功，打开它给的 `*.pages.dev` 网址。
5. 逐页点一遍，再用手机打开看一次，都正常才算部署完成。

### 部署失败怎么办

先打开这次部署的构建日志，第一条真正的报错才是原因。最常见的是构建命令或产物目录和本地填得不一致，而不是页面写错了。把报错原文复制给 Claude Code 让它判断；改完推送一次，就会自动重新部署，不用手动再点一遍。

### 最后收尾

1. 把线上网址写进 README 第一行，再在末尾写 100–200 字复盘：你的总提示词原文、AI 给过你什么惊喜、微调时你改了什么。
2. 提交并推送一次，确认 Cloudflare 部署状态仍是成功：

```bash
git add . # 把改好的 README 和收尾改动放进暂存区，准备提交
git commit -m "docs: 补线上网址和复盘" # 把收尾这一版正式存成一次提交
git push # 把收尾提交推到 GitHub，Cloudflare 会跟着自动重新部署
```

3. 按学长课后通知的方式提交线上网址，作业完成。

### Git 命令（在项目文件夹里，`#` 后面是这一条干了什么）

```bash
git init # 初始化本地仓库：在当前文件夹生成 .git，开始记录版本
git branch -M main # 把当前分支改名为 main，和 GitHub 主分支名一致
git remote add origin 【仓库地址】  # 把 GitHub 上的空仓库登记为远程仓库 origin，之后才能往它推
git add . # 把所有新文件和改动放进暂存区，准备提交
git commit -m "init: 初始化仓库" # 把暂存区内容正式存成第一次提交
git push -u origin main # 第一次推送：把 main 推到 origin，并记住默认推送目标
git push # 之后每次推送：把新提交推到已记住的远程仓库，不用再写全
```

### Git 进阶演示命令（学长演示用，练习仓库 git-playground 里敲，不在网站仓库里敲）

```bash
git clone 【仓库地址】 # 把远端仓库完整复制一份到本地，并自动连好 origin
git remote -v # 查看本地仓库连着的远端地址，确认 origin 指向哪里
git branch # 查看本地分支列表，带 * 的是当前所在的分支
git switch -c feature/演示 # 新建一条分支并切换过去，在这条分支上改动不影响 main
git switch main # 切回 main 分支
git merge feature/演示 # 把指定分支的改动合并进当前分支
git branch -d feature/演示 # 删掉本地已经合并完的分支
git push -u origin feature/演示 # 第一次把这条分支推到远端，并记住它的对应关系
git push origin --delete feature/演示 # 删掉远端上的同名分支，本地删和远端删要分开做
git fetch # 只下载远端最新状态看看，不改本地正在写的文件
git pull # 下载远端新提交并直接合并进当前分支，等于 fetch 加 merge
```

## 写在最后：学长的几句话

做到这里，学弟学妹们的第一个个人网站就已经在 GitHub 上了，课后把 Cloudflare 部署补完，它就会有一个全世界都能打开的网址。这件事听起来不大，但它其实是你们很多人第一次把「我做的东西」真正放到了互联网上，这一步不少人都是自己摸索很久才走通的，你们一节课就走完了。

再叮嘱三件小事：

- **别怕改坏。** 每次提交都是一次存档，改坏了随时能退回上一版。想练分支，就回家在 `git-playground` 里随便练，练坏了删掉重建，不心疼。
- **提示词先放开，再收紧。** 先让 AI 给你惊喜，不满意再一句一句往回收，这个顺序反过来，好想法就没机会出现了。
- **做完把网址发出来。** 发到群里也好，写进简历也好，让别人打开看一眼，这个网站才算真正活过来了。
